# Progress Report 05: kernel port milestones 2 and 3 green (POP1 + per-group merge)

## Milestone 2: a partition harness that can fail

`bin/sd-pop` runs 4 nodes in containers with `NET_ADMIN`:
- g1 = {a, r, x}, g2 = {x, y};
- it cuts a↔x with `iptables` (a real pairwise partition, detected in about
  5 s with `net_ticktime 4`);
- a and x register the same g1 name for different pids;
- it checks that g2 is unaffected (P8);
- it heals and re-dials, as an application or libcluster would (decision
  RC1).

It runs twice, registering on a first and then on x first.

On the **milestone-1 kernel**: during the cut, r held the last writer's pid.
After the heal, a and x converged on the smaller pid, so the x-first order
left r on a's pid **permanently**. That's the overlapping-partition hazard
from D-5, observed in a real network split.

## Milestone 3: POP1 + per-group merge

`patches/otp29/0002` adds a per-group in-sync set `K[G]` to `s_group`:

- Name operations lock and multicast within `{self} ∪ K[G]`.
- **POP1:** a node that loses a fellow member reports `pop_lost` with its
  link incarnation to the rest of its partition. Receivers drop the far end
  from that group's set, logically: no link is cut and other groups are
  untouched. Reports older than a merge stamp are ignored, as in
  `SGroupPOPHeal` `logical_epoch`.
- **Merge (R-NS-1):** a tick merges in connected members missing from
  `K[G]`. The smaller node initiates, and a larger node with an asymmetric
  view asks it to. The merge runs under one lock on both partitions and
  requires full connectivity. It resolves conflicts as 19.3 does
  (`random_exit_name`: keep the smaller pid, kill the other) and keeps one
  name per pid (U1).

**Result:** both `bin/sd-pop` orders pass. During the cut, r stays
consistent with a's side and x is alone; after the heal, all three hold one
live pid.

## Found on the way

**A boot deadlock**, caught by the image build. The build compiles later
modules with an already-patched kernel, and those VMs hung at boot.
`timer:send_interval/2` in `s_group:init/1` waits for `timer_server`,
which is only started after the kernel's own children. Any node booting
that kernel would have hung. Fixed with `erlang:send_after/3`.
